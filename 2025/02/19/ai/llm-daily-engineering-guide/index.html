日常生活、工作与工程中用好大模型：能力、平台、Prompt 与学习规划

Posted on 2025-02-19 In AI Word count in article: 9.1k Reading time ≈ 8 mins.

本文系统梳理：大模型在日常生活、工作与工程中的可应用能力（其中开发与代码工程为最重要的一环）、常用大模型应用平台（含官网/APP、能力、免费与收费、推荐等级）、高质量 Prompt 写法，以及提升大模型应用能力的规划与学习资料。参考资料均来自官方网站或专业机构。

一、大模型在日常生活、工作与工程中可应用的能力

开发与代码工程是其中最重要的一环，同时大模型也可广泛用于日常沟通、信息获取、写作与办公等场景。下面按场景分类。

1. 代码相关（工程核心）

能力 应用场景 使用建议
代码生成 从需求/注释生成函数、脚本、测试、脚手架 给出清晰输入输出与约束，指定语言和框架
代码补全 行级/块级补全、整段生成 在 IDE 中配合 Cursor/Copilot/Continue 等使用
代码解释 解释陌生代码、算法、依赖关系 贴代码+简短上下文，可要求「用中文/分步骤」
代码重构 重命名、抽取函数、去重复、提升可读性 明确「保持行为不变」「先给方案再改」
Bug 定位与修复 根据报错、日志、复现步骤分析原因并给补丁 提供完整错误信息、环境、最小复现
代码审查 风格、安全、性能、可维护性建议 提供 PR 片段或文件+业务背景，可要求按 checklist 输出
单元测试 根据实现写测试用例、边界情况、Mock 说明测试框架和覆盖率期望
文档生成 函数/API 文档、README、变更说明 指定格式（如 JSDoc、OpenAPI）和受众

2. 设计与协作

能力 应用场景 使用建议
架构与方案 技术选型、模块划分、接口设计、演进建议 写清约束（性能、团队、历史包袱）和决策点
需求拆解 用户故事 → 任务列表、验收标准、依赖关系 分步骤提问，必要时用表格/列表约束输出
文档与沟通 会议纪要、RFC 摘要、邮件/周报草稿 提供要点列表，要求「简洁/正式/非技术」等风格
正则与脚本 写/解释正则、Shell/Python 一行脚本、小工具 给样例输入输出，说明环境（bash/zsh、Python 版本）

3. 学习与检索

能力 应用场景 使用建议
概念解释 技术概念、协议、最佳实践 指定「面向初学者」或「面向有 X 经验的人」
对比与选型 库/框架/方案对比、优缺点、适用场景 限定维度（性能、生态、学习成本等）
故障排查 根据报错信息查原因、查官方文档要点 贴完整报错+环境，要求引用文档或给出链接
读书/文档总结 长文摘要、章节要点、行动清单 分段处理长文档，或先给目录再按章节问

4. 日常生活与通用工作

能力 应用场景 使用建议
写作与润色 邮件、周报、演讲稿、文案、翻译 说明语气（正式/口语）、受众与长度
信息检索与总结 时事、百科、新闻摘要、深度调研 用带联网的模型（如 Perplexity、Kimi）并要求标注来源
学习与答疑 外语、考试、技能入门、读书笔记 分步提问，要求举例或出题巩固
日程与待办 行程整理、会议要点、待办列表 给原始信息，指定输出格式（列表/日历）
办公辅助 表格处理、PPT 大纲、文档模板 说明格式与约束，复杂表格可分段处理
娱乐与创意 故事、脑洞、角色设定、简单剧本 明确风格与禁忌，可多轮迭代

5. 使用时的注意点

  • 幻觉与过时：模型可能编造 API、版本号或最佳实践，关键处需查官方文档或运行验证。
  • 安全与隐私：勿把密钥、内部架构、未脱敏数据贴到公开在线模型；用本地或企业允许的接口时也要遵守合规。
  • 人做最终决策：代码审查、架构决策、发布前变更建议由人做最终确认，大模型做辅助。

三、如何写出好的 Prompt

1. 基本原则

  • 具体、可执行：避免「帮我优化一下」，改为「用 TypeScript 重写下面函数，保持相同入参和返回值，并加上 JSDoc」。
  • 给足上下文：说明角色（你是什么身份）、任务（要干什么）、约束（不能做什么、必须用什么）。
  • 结构化：用标题、列表、分隔符（如 ---、"""）区分：角色、背景、输入、输出格式、示例、注意事项。
  • 分步拆解：复杂任务拆成多轮小问题，或在一个 Prompt 里写清「第一步…第二步…」。
  • 指定输出形式：要 JSON、表格、列表、代码块、中英文等，直接写明。

2. 常用技巧

技巧 说明 示例
角色设定 让模型扮演某类专家 「你是一位有 10 年经验的 React 性能优化专家。」
Few-shot 给 1–3 个输入输出示例 「输入：… 输出：… 请按同样风格处理下面内容。」
Chain-of-Thought 要求先推理再给结论 「请先分析可能原因，再给出修改建议和示例代码。」
约束与禁止 明确不要做的事 「不要使用已废弃的 API」「不要解释，只给代码。」
输出格式 用 Markdown/JSON/列表 约束 「用表格列出优缺点」「返回 JSON：{ “steps”: [] }」
分步执行 把大任务写成步骤 「第一步列出所有接口；第二步为每个接口写一个测试用例。」

3. 编程场景的 Prompt 模板示例

4. 迭代优化

  • 若回答太泛：加「只回答…」「不要…」「最多 N 条」。
  • 若漏了关键点：在 Prompt 里显式列出「必须包含：1…2…3…」。
  • 若格式不对：给一个期望输出的样例（few-shot）。
  • 若模型「跑偏」：新开对话，把上一轮里好的表述固化进新 Prompt 的开头。

四、系统提升大模型应用能力的规划

阶段一：建立习惯（约 2–4 周）

  • 目标：每天至少 1 次用大模型完成真实工作项（查错、写小函数、写注释、写邮件）。
  • 行动：
    • 选 1 个固定入口（如一个常用网页端或 Cursor），统一从「小任务」开始。
    • 记录 3–5 个「用了就有效」的场景（如：解释报错、写单元测试、生成正则）。
  • 检验：能不看教程，独立完成「贴代码 → 得到可用的修改/解释」。

阶段二：提升 Prompt 质量（约 4–6 周）

  • 目标：同样任务，用更少的轮次、更稳定的格式得到可用结果。
  • 行动：
    • 为高频场景写 3–5 个「个人模板」（如：代码审查、写测试、写 README）。
    • 练习：角色 + 任务 + 约束 + 输出格式，四要素都写全。
    • 尝试：Few-shot、分步执行、Chain-of-Thought 各至少用几次。
  • 检验：一个新任务，第一次发的 Prompt 就能拿到 80% 可用的结果。

阶段三：融入工作流（约 2–3 个月）

  • 目标：把大模型嵌进需求分析、开发、审查、文档、排错全流程。
  • 行动：
    • 需求/设计：用模型做「用户故事拆解」「接口清单」「方案对比」。
    • 开发：用 IDE 集成做补全、生成测试、小重构。
    • 审查：用固定 Prompt 对 PR 做风格/安全/复杂度检查（人做最终决定）。
    • 文档：用模型写/补全 API 说明、README、发布说明。
  • 检验：能在 1–2 个真实项目里，从需求到发布都有一环用到模型辅助。

阶段四：进阶与复用（持续）

  • 目标：能设计可复用的提示、简单自动化（如脚本调用 API）、并判断何时不用模型。
  • 行动：
    • 把常用 Prompt 整理成团队文档或 Cursor Rules。
    • 了解 RAG、Agent、Function Calling 等概念（用于「查知识库」「调工具」）。
    • 定期回顾：哪些场景用模型反而更慢或质量更差，明确「不用」的边界。
  • 检验：能向同事说明「这类问题适合用模型，这类不适合」。

六、小结

  • 能力：除开发与代码工程（最重要一环）外，还覆盖日常生活与通用工作（写作、信息检索、学习、日程、办公等）；架构与需求拆解、学习与排错同样可应用；注意幻觉与安全，人做最终决策。
  • 平台：对话与多模态见 2.1 表（序号 1～18），含 ChatGPT、Claude、Gemini、Copilot、Perplexity、DeepSeek、Poe、文心/通义/豆包/元宝/Kimi/扣子 Coze/智谱/天工/零一万物 Yi/Grok、Mistral 等；图像/视频见 2.2 表（序号 1～7），含 DALL·E、通义万相、即梦、可灵、智谱清影、文心一格、Gemini；编程见 2.3 表（序号 1～9），含 Cursor、Copilot、通义灵码、文心快码 Comate、CodeBuddy、MarsCode、Windsurf、Continue、Ollama。每类平台均附有推荐等级打分维度分析表，便于按维度理解最终星级。
  • Prompt：具体、给足上下文、结构化、指定输出；善用角色、Few-shot、分步、Chain-of-Thought；编程场景用「角色+任务+输入+约束+输出格式」模板。
  • 提升路径：建立每日使用习惯 → 优化 Prompt 与模板 → 融入需求/开发/审查/文档全流程 → 复用与边界判断；学习以官方网站与专业资料为主，并定期更新平台列表与个人模板。
